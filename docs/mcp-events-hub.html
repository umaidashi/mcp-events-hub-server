MCP Events Hub
サービスとエージェントの間で、イベントを中継する

上流サービスは イベント定義の登録と、署名付き webhook の送信だけを実装します。クライアントエージェントは ハブ 1 か所に接続し、全サービスのイベントを 1 つのカタログから購読します。配信は MCP Events ドラフト仕様の poll、push、webhook の 3 方式すべてに対応し、特定のベンダーに依存しません。

全体像

サービスはハブに送るだけ、クライアントは好きな方式で受け取る

なぜハブか

組み合わせの数だけあった実装を、サービス数とクライアント数の和に減らす

中心のデータ構造

ハブの中身は 1 本のイベントログ。3 つの配信方式はその読み方の違い

受け取ったイベントは、到着順の連番 seq を付けて追記します。どの方式でも cursor はこの連番で、「どこまで受け取ったか」を表します。再接続や再購読のときに cursor を渡せば、ログから続きを読み直せます。

1 件のイベントの流れ

注文が 1 件入ってから、エージェントが返事をするまで

通信の形式

届く中身は 3 方式で同じ。違うのは、誰が接続を始めて、どう運ぶか

イベント本体は共通で、{ eventId, name, timestamp, data, cursor } の形をしています。下の例は、ハブを実際に動かして取った通信です。

購読の条件は「payload の同名フィールドとの完全一致」だけ

サービスが登録する inputSchema の各プロパティは、payloadSchema にある同じ名前のフィールドと比べる条件になります。payload にないフィルタは登録時に拒否します。ハブはサービスごとの条件の意味を知らなくても照合でき、3 つの方式すべてで同じ判定になります。

購読 shop.order.created {"customer": "alice"}
イベント data {"order_id":"o-alice-1","customer":"alice", …} customer が一致するので届く
イベント data {"order_id":"o-bob-1","customer":"bob", …} 一致しないのでログに残るだけ
pi/mcp-events.ts

pi の拡張は、イベントを「エージェントの次のターン」に変える

pi は MCP のツールとリソースには対応していますが、MCP Events には対応していません。拡張がその部分を受け持ちます。拡張はハブのコードを読み込まず、通信仕様だけで話すので、MCP Events を話す他のサーバーにもそのままつながります。

カタログを見る

events_catalogイベント名、条件に使える引数、payload のフィールドを一覧にし、いまの購読も表示します。

購読する

events_subscribe名前、条件、届いたときの指示を受け取ります。ストリームが開くか最初の poll が成功してから結果を返すので、失敗はその場でわかります。

イベントが届く

sendMessage(triggerTurn)eventId で重複を除いてから会話に入れ、新しいターンを起こします。payload は「外部から来た信頼できないデータ」と明記して渡します。

使い方

ローカルで動かす

依存パッケージはなく、Node.js 24 以上で .ts をそのまま実行します。

  1. ハブを起動します。

    HUB_ADMIN_TOKEN=dev-admin HUB_CLIENT_TOKENS=pi:dev-client \
HUB_ALLOW_PRIVATE_CALLBACKS=1 npm start

  2. モックの shop サービスを登録し、注文を送ります。

    npm run mock -- register
npm run mock -- emit order.created \
  '{"order_id":"o-1","customer":"alice","amount":1200,"currency":"JPY"}'
npm run mock -- loop 5      # 5 秒ごとにランダムな注文

  3. pi を拡張付きで起動し、「shop.order.created を customer=alice で購読して、届いたら金額を報告して」と頼みます。

    MCP_EVENTS_HUB_URL=http://127.0.0.1:8787/mcp \
MCP_EVENTS_HUB_TOKEN=dev-client \
pi --extension pi/mcp-events.ts

  4. 通しで確かめるときは、リポジトリ直下の .env に ANTHROPIC_API_KEY を書いてからデモを実行します。.env は git の管理対象外です。

    npm test        # LLM を使わない 31 件
npm run demo    # push / poll / webhook を実際の pi と Claude で 1 回ずつ

試作で割り切った点

  • webhook 本文の cursor は、そのイベント自身の連番です。再送待ちのイベントを考慮した値ではないので、保存した cursor が再送待ちの古いイベントを飛ばすことがあります。
  • callback 先はプライベートアドレスを拒否していますが、名前解決した接続先を固定していません。DNS rebinding の余地があります。
  • gap と terminated の通知、カタログ変更の通知、events/list のページング、secret ローテーション時の二重署名、失敗率による配信停止は未実装です。
  • JSON Schema の検証は type、properties、required、additionalProperties: false、enum、items だけです。
  • 拡張側の重複除去はテストで押さえていません。同じイベントの二重送信はハブが受信時に 1 件にまとめるため、再接続で二重に届く場合が残っています。
  • 認証は静的な Bearer トークンです。公開して使うなら OAuth に置き換えます。
